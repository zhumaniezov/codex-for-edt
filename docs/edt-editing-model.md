# Модель редактирования EDT

Решение развивает работающий native слой 0.7. Основание: [официальный integration layer](https://edt.1c.ru/dev/ru/docs/plugins/dev/model/integration/) и публичные сигнатуры EDT 2026.1.3.25.

| Контекст | Штатное поведение | Применимость |
| --- | --- | --- |
| Global | Успешные задачи сохраняются автоматически; подходит панелям и refactoring | Правильный общий механизм, но экспорт асинхронный. Не считаем ответ инструмента доказательством завершённого resource save |
| Local | История, canUndo/canRedo, undo/redo, dirty, explicit save, dispose отменяет несохранённые изменения | Один изолированный Metadata Change Plan; понятный момент завершения через save(true) |
| executeReadWriteTask | Транзакция вне editing context | Не используется для сохраняемых изменений агента |
| executeImportTask | Импорт может затрагивать локальные редакторские контексты | Не используется как обход dirty guard |

Выбран **local editing context на согласованный план**. Он не принадлежит пользовательскому редактору. Сначала проверяется структура всего плана. Корневые объекты создаются в предварительной задаче; последующие операции выполняются последовательными задачами того же context. Между зависимыми задачами ожидаются события и производные данные через IDerivedDataManagerProvider / waitAllComputations: новые ссылочные типы и поля DbView нельзя использовать до расчёта EDT. Единственный save(true) вызывается после успеха всех задач. При исключении dispose отменяет все несохранённые задачи этого context, а не только последнюю. Это проверено на плане с созданием справочника и ошибкой последующей формы. EObject не выходит за границу своей транзакции: результаты — независимые DTO. Изменения уже видны другим BM-потребителям до save: это не изоляция snapshot для всей последовательности. Повторяемая EDT задача не меняет внешнее состояние, влияющее на её повторный запуск при deadlock.

Undo/Redo публично доступен: локальный context предоставляет getUndoContext/canUndo/canRedo/undo/redo. Временный context 0.7 освобождался после сохранения, поэтому пользовательский Undo не обещался. Удержание истории требует отдельной политики владения, обработки конфликтов с пользовательскими редакторами и штатного связывания с workbench operation history. Это не эквивалент git reset и не даёт права отменять пользовательские изменения.

BSL построен из текста и не сериализуется обратно из AST. Для text edits применяется document/resource слой Xtext, а не изменение AST с ожиданием, что EDT сгенерирует код. Атомарность BM-задачи не распространяется автоматически на отдельную запись Xtext-документа или отказ файловой системы; границы составных операций и частичный отказ должны быть явно отражены в результате.

До write turn сохраняется действующий dirty guard. Только явное «Сохранить и продолжить» разрешает сохранение пользовательских buffer. Read-only исключает мутации; Strict требует подтверждения каждого плана. Истёкший turn и закрытая View не могут подтвердить новый план.
