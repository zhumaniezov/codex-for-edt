# Архитектура версии 0.2

## Слои

| Компонент | Ответственность |
| --- | --- |
| `CodexView` | SWT/JFace, ввод, состояние, потоковое отображение |
| `EclipseContextProvider` | Активный редактор, файл, выделение и физический каталог проекта |
| `EditorContext / ChatRequest` | Неизменяемые данные без живых объектов Eclipse |
| `CodexSessionService` | Handshake, вход, модель, cwd, thread/turn и события |
| `ReadOnlyPolicy` | Параметры режима чтения, проверка ответа сервера, компактный контекст |
| `CodexAppServerClient` | JSONL, ID запросов, ответы, уведомления, ошибки и тайм-ауты |
| `CodexProcessManager` | Дочерний процесс, отдельные потоки STDOUT/STDERR и завершение |
| `CodexExecutable` | Поиск файла и проверка версии |
| `CodexPlugin` | Жизненный цикл bundle, Error Log, закрытие созданных клиентов |

Идентификатор bundle: `io.github.zhumaniezov.codex.edt`. Идентификатор панели: `io.github.zhumaniezov.codex.edt.views.Codex`. UI зарегистрирован через публичное расширение [org.eclipse.ui.views](https://help.eclipse.org/latest/topic/org.eclipse.platform.doc.isv/reference/extension-points/org_eclipse_ui_views.html).

Структура проекта сохраняет официальный подход 1С: `bom`, `targets`, `bundles`, `features`, `repositories`, `tests`. В поставке одна feature и один рабочий bundle; тесты не устанавливаются. Gson берётся из Target Platform/установленной EDT.

## Потоки выполнения

SWT-поток собирает снимок контекста и обновляет элементы интерфейса. В нём нет ожидания процесса, RPC или ответа модели.

Каждая сессия имеет последовательный фоновый executor. Отдельные потоки читают UTF-8 STDOUT и STDERR. Ответы RPC завершают соответствующие futures; события передаются executor сессии. Запросы имеют уникальные числовые ID, а ключи сопоставления сохраняют различие строковых и числовых ID.

View получает обновления через `Display.asyncExec`. Частые текстовые события объединяются перед отрисовкой, чтобы не переполнять очередь SWT. Проверка dispose предотвращает доступ к уничтоженным виджетам.

## Соединение и диалог

При открытии панели выполняются поиск Codex, проверка версии, запуск процесса, `initialize`, `initialized`, `account/read` и `model/list`. ClientInfo принадлежит проекту: `codex_edt`, `Codex for 1C:EDT`, версия bundle.

Флаг `requiresOpenaiAuth` проверяется вместе с наличием account. Существующий вход использует сам app-server. Плагин не открывает auth.json, не получает OAuth-токены и не сохраняет учётные данные.

Модель выбирается из всех страниц каталога: isDefault, иначе первая видимая. На первом Send создаётся временный thread. Последующие запросы в том же физическом проекте используют его повторно. При смене проекта или переподключении создаётся новый. Собственного хранилища истории нет.

## Контекст и cwd

Через `IWorkbenchPage.getActiveEditor()` получается активный редактор. Для `MultiPageEditorPart` выбирается текущая страница-редактор. Далее используются публичные `ITextEditor`, `ResourceUtil.getFile()`, `IProject` и `ITextSelection`.

Физический путь берётся из `IProject.getLocationURI()`. Разрешены file URI; фоновый слой проверяет существование каталога и приводит его к реальному пути. Путь ресурса вида `/Проект/src/.../Module.bsl` не используется как cwd. Внешнее расположение проекта сохраняется.

В сообщение включается только компактный снимок: имя проекта, путь модуля, непустое выделение и запрос. Выделение ограничено 16000 символами с явной пометкой. Ввод ограничен 32768 символами, вывод панели — 1 МиБ символов. Полный файл автоматически не читается.

Текст берётся из памяти редактора, поэтому несохранённое выделение доступно. Семантическая модель `IV8Project`, БМ, AST, Compare Editor и нетекстовые страницы остаются вне текущего объёма.

## Защита режима чтения

- В thread задаются `sandbox:read-only`, `approvalPolicy:never` и `approvalsReviewer:user`.
- В каждом turn задаются `sandboxPolicy.type:readOnly` и `networkAccess:false`.
- До turn проверяются фактически возвращённые sandbox, approvalPolicy, модель и cwd.
- Имена настроенных MCP-серверов получаются через `config/read`; только для этой сессии им задаётся enabled:false. Значения настроек не копируются и не журналируются.
- Дополнительные средства действий отключены параметрами процесса и диалога: приложения, плагины, hooks, браузер, управление компьютером и субагенты. Обычные команды чтения остаются под контролем песочницы Codex.
- Неожиданный запрос действия от сервера отклоняется, соединение закрывается. Клиент не выдаёт разрешения.
- Глобальные config.toml, MCP и skills не изменяются. Сам Codex вправе вести свои штатные служебные данные и авторизацию.

Точные поля основаны на схеме установленной версии, а не на предположениях: [исследование app-server](app-server-research.md).

## События и ошибки

Обрабатываются `turn/started`, `item/agentMessage/delta`, `item/completed`, `turn/completed` и `error`. Фрагменты разных сообщений разделяются по itemId; события другого thread/turn игнорируются. При отсутствии delta завершённое agentMessage восстанавливает текст.

`error.willRetry:true` оставляет запрос активным; окончательная ошибка возвращает понятное сообщение. RPC ограничен 45 секундами, выполнение — пятью минутами. При повреждённом JSONL, закрытии STDOUT или зависании процесс отключается, ожидающие запросы завершаются ошибкой.

STDOUT и содержимое запросов не журналируются. STDERR читается отдельно, ограничивается по длине и очищается от типовых форматов секретов. Ошибки со стеком направляются в Eclipse Error Log; в пользовательской области показывается сообщение без стека.

## Закрытие

Закрытие View и остановка bundle инициируют завершение собственных клиентов. Сначала закрывается stdin, затем даётся ограниченное время для штатного выхода. При необходимости завершаются собственный процесс и отслеженные потомки. Поиск и уничтожение процессов по имени не применяется.

Завершение выполняется отдельным ограниченным по времени потоком, который не блокирует SWT и не даёт JVM выйти раньше уборки. Чужие процессы Codex не затрагиваются.

## Тестирование

Для воспроизводимых тестов клиентская фабрика подменяется через стандартный OSGi service. Тестовый Java app-server общается по настоящим дочерним stdio pipes. В обычной поставке test bundle отсутствует, используется реальный клиент.

Реальный тест включается отдельно через `-Smoke -Live`; он использует тот же сервис сессии и Codex View, проверяет частичный ответ до завершения и хеши файлов. Результаты — в [testing.md](testing.md).
