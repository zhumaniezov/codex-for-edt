## Обязательный dirty-editor тест

1. Откройте общий модуль конфигурации в настоящем BSL-редакторе EDT.
2. Сохранённый `Module.bsl` может оставаться пустым. Вставьте в редактор, **не сохраняя**:

```bsl
Процедура Тест()
    Сообщить("Привет");
КонецПроцедуры
```

3. Убедитесь, что на вкладке есть `*`. Снимите выделение, **не нажимайте Ctrl+S**.
4. В Codex спросите: **«Какой код сейчас находится в открытом модуле?»**.
5. В ответе должна быть именно процедура `Тест` с `Сообщить("Привет")`, а не только утверждение, что файл на диске пустой.
6. Выделите `Сообщить("Привет");`.
7. Спросите: **«Что делает выделенный код и в каком контексте он находится?»**.
8. Codex должен объяснить вызов внутри несохранённой процедуры. Звёздочка остаётся, файл не сохраняется.
9. Повторите с большим модулем: окно ограничено 48 000 символами. Codex должен знать, что это фрагмент, и не заявлять, что получил весь несохранённый модуль.

## SHA-256 без изменения проекта

В PowerShell задайте **фактический каталог тестового проекта**, показанный в tooltip диагностики. Перед первым хешированием дождитесь окончания фоновых операций EDT. Не используйте каталог всей workspace с `.metadata`: сама EDT меняет служебные файлы.

```powershell
$testProject = 'C:\путь\к\тестовому-проекту'
$before = @(Get-ChildItem -LiteralPath $testProject -Recurse -File |
    Sort-Object FullName | Get-FileHash -Algorithm SHA256 |
    ForEach-Object { $_.Path + ' ' + $_.Hash })
# Здесь выполнить запрос в Codex. Dirty-документ не сохранять.
$after = @(Get-ChildItem -LiteralPath $testProject -Recurse -File |
    Sort-Object FullName | Get-FileHash -Algorithm SHA256 |
    ForEach-Object { $_.Path + ' ' + $_.Hash })
Compare-Object $before $after
```

Пустой вывод означает равенство. Если EDT параллельно пересобирала проект, разберите отличающиеся пути; не приписывайте их автоматически агенту. Автоматические сценарии используют изолированный файловый проект и сравнивают все его файлы.

## Ограничения и диагностика

Версия 0.3 вручную принята автором: настоящая конфигурация, BSL-редактор, dirty buffer и selection, один thread для последовательных запросов, New/Resume, модель/reasoning, Stop, обе темы, Account, Preferences и Enter/Shift+Enter. Markdown тогда не считался проверенным; для него выделен TC-22.

UI установки ZIP в основную EDT, PDE Debug, другие версии Codex/EDT, сетевые и удалённые с диска каталоги, Compare Editor и редакторы без публичного ITextEditor не считаются проверенными этой сборкой. История показывает текст пользователя/ассистента; подробные tool items пока скрыты. Большой dirty-модуль передаётся окном, точный diff не вычисляется. HTTP(S)-ссылки поддерживаются; файловая навигация отложена.

При подготовке UI-тест обнаружил неправильную доставку snapshot и ограничение native placeholder для многострочного Text в Windows; оба исправлены. Live-тест теперь ждёт именно готовую кнопку ↑ и проверяет два серверных ответа, а не промежуточное состояние после Stop.

Известные сообщения хостовой EDT: отсутствие `wmic` в Windows 11, дублирующееся расширение ServersView, working-set filter Resource Navigator. Они не являются ошибками Java-кода плагина. Tycho предупреждает о p2-зависимостях в consumer POM; проверка OSGi/p2 выполняется отдельно.

При ошибке смотрите **Window → Show View → Error Log** и `.runtime/.../edt.log`. Не исправляйте её включением полного доступа. Глобальные Codex config/MCP/Skills не меняются. Следующий этап до отдельного решения автора не начинается.


## Диагностика restore для v0.3.1

Проверен исходный журнал `.runtime/development/workspace/.metadata/.log`, в том числе сессии **11.09.2026 19:33:02 и 19:47:02** (EDT 2026.1.3.25, Java 17.0.18). Фактическая рабочая область находится внутри `C:\projects\codex-edt\.runtime`, а не в соседней `codex-edt.runtime`. В этих сессиях **нет записи с первичным исключением нашего bundle**, класса `CodexView`, `Caused by` или строки нашего Java-кода, объясняющей Error Part. Ошибки WMIC, stylesheet EDT и navigator относятся к другим bundle и не объявлены причиной дефекта.

Предоставленные строки сопоставлены с [официальным ViewReference.java Eclipse R4_30](https://github.com/eclipse-platform/eclipse.platform.ui/blob/R4_30/bundles/org.eclipse.ui.workbench/Eclipse%20UI/org/eclipse/ui/internal/ViewReference.java#L98). В `org.eclipse.ui.internal.ViewReference.createPart():101` вызывается `createErrorPart()` при **`descriptor == null`**. На строке **115** Eclipse сам создаёт `new Exception()` для Error Part. В этой ветке **нет вызова конструктора CodexView**; дополнительного `Caused by` у созданного таким образом исключения нет. Источник дескриптора — `WorkbenchPage.createViewReferenceForPart():1980`, поиск через `getViewRegistry().find(descId)`; `ViewRegistry.find():211–215` учитывает также ограничения activities. Это подтверждённый механизм данного короткого стека, но причина отсутствия дескриптора в конкретном запуске пока не установлена.

Сохранённая перспектива содержит и текущий id панели, и неактивную ссылку на старый id из начальной версии. Наличие старой ссылки **не доказывает**, что пользователь видел именно её Error Part. Для установления исторической причины потребовался бы полный id из заголовка/сообщения ошибки. Воспроизведение не заменяется удалением `.metadata`, `workbench.xmi` или preferences.

Проверки исходной v0.3 до функциональных изменений:

- Два процесса полного EDT с одной рабочей областью: открытие, штатное закрытие с открытой View, restore. **Текущая View восстановилась**, даже с недоступным Codex executable (`.runtime/edt-restart-baseline2`).
- Копия пользовательской перспективы и копия configuration cache: текущая View создалась. Отдельная проверка отсутствия активного editor в этих копиях не подходит — в сохранённом состоянии присутствует редактор метаданных; это не ошибка Codex.
- Изолированная копия конфигурации и независимый startup-наблюдатель **без зависимости от Codex bundle**: восстановлен класс `io.github.zhumaniezov.codex.edt.ui.CodexView`, дескриптор доступен, bundle ACTIVE, версия `0.3.0.v20260911191850`. Данные наблюдения лежат в игнорируемой `.runtime/restore-observer`; первоначальный workspace не изменялся. Подключений к информационной базе копия не содержит.

**Вывод:** изменения lifecycle ниже проверены, но объявлять первопричину исходного startup failure найденной или дефект окончательно устранённым пока нельзя. Автор подтвердил успешную ручную приёмку hardened lifecycle. Это позволяет выпустить 0.3.1, сохранив неопределённость исторической причины.

ToolPlatform проверяет native API без OpenAI. ToolPlatformLive использует существующую авторизацию Codex и реальную модель; тестовая автоматизация принимает только подтверждения своего native MCP и native планы, отклоняет file/command approvals. Он создаёт специальный проект, проверяет четыре запроса одного thread и удаляет свою фикстуру. Скопированные результаты native save остаются в `native-artifacts` рядом с result.txt; это диагностические артефакты, не исходники плагина.

### Важные результаты диагностики реализации

- В модели есть transient служебные Type, не являющиеся файлами проекта. Присоединять любой non-containment EObject как внешний ресурс неправильно. Адаптер присоединяет только native module/form/role-description; канонический уже существующий module получает по native FQN.
- Новые producer types/DbView требуют завершения derived computations. Один model-event barrier недостаточен. Ожидание штатного менеджера выполняется вне BM-задачи.
- Пустому невыгруженному Module.bsl нужен URI opener EDT; обычный FileEditorInput не гарантирует документ. Уже открытый editor переиспользуется.
- EDT повторяет задачу при BM deadlock. Внешнее состояние не изменяется внутри повторяемого callback. Dispose local context откатывает несколько несохранённых задач; это проверено отдельно от preflight failure.
- Стенд close/open должен дождаться lifecycle DELETED и закрытия своих редакторов. Это не обоснование удаления workbench state или пользовательского workspace.
- Первый live-прогон обнаружил необработанный mcpServer/elicitation/request. Добавлена проверка своего server/thread/turn и пустой approval-schema; поддержка произвольных elicitation forms не имитируется.
- Повторный live-прогон выявил отдельный конфликт защиты редакторов с native URI opener: `ProjectWriteGuard.lockEditors` получал `partActivated` ещё внутри `AbstractTextEditor.init`, когда embedded BSL control HTTP-сервиса не создан. Собственное открытие теперь ограничено UI-вызовом `openNativeEditor`; сразу после возврата opener выполняется полная проверка dirty state и блокировка controls. Чужие открытия и неизвестные редакторы по-прежнему отклоняются, защита записи не выключается. Регрессия открывает второй native BSL editor при активной защите. Это не доказательство причины старого startup Error Part версии 0.3.
