## Автоматические тесты без OpenAI

- повторное подключение, закрытие с незавершёнными операциями;
- завершение своего процесса и его потомка при сохранении отдельного постороннего процесса;
- остановка сервера, который совсем не читает STDIN: заполненный pipe не задерживает завершение.

`CodexViewTest` сохраняет сценарий первой версии с тестовым клиентом: регистрация настоящей SWT View, Send, проект, BSL-путь, физический каталог, выделение из несохранённого документа после перехода фокуса в чат, очистка устаревшего контекста, закрытие и повторное открытие панели. Заглушка находится только в тестовом bundle.

`StreamingViewTest` проводит запрос через настоящую View и все рабочие слои клиента к тестовому дочернему серверу. Проверяются постепенное обновление текста, состояние Send, cwd, SHA-256 всех файлов временного проекта и завершение процесса после dispose.

Тесты проверяют поведение через JSONL и SWT; они не подменяют рабочую View.

## Реальный end-to-end с OpenAI Codex

Команда:

```powershell
.\scripts\start-dev-edt.ps1 -Smoke -Live
```

Требуются установленный Codex, уже действующий вход и доступ к сервису. Это настоящий запрос, расходующий лимиты пользователя.

**Реальный тест итоговой поставки успешно выполнен в development EDT** в `.runtime/edt-smoke-20260911174320`: **PASS, tests=1, failures=0**. Через `model/list` обнаружена модель **gpt-6-astra**, получено **23 обновления текста в SWT**. После успешного ответа проверено завершение процесса, созданного панелью. Число обновлений панели может отличаться от числа delta в протоколе: частые обновления объединяются перед asyncExec.

Сценарий:

1. Создать уникальный временный Eclipse-проект внутри отдельной workspace EDT.
2. Создать `Module.bsl` с текстом `Сообщить("Привет");`.
3. Снять SHA-256 всех файлов проекта.
4. Открыть файл, выделить код, открыть Codex View.
5. Дождаться initialize, проверки входа и выбора модели.
6. Ввести **«Что делает выделенный код?»** и нажать Send.
7. Создать thread с физическим каталогом именно этого проекта и read-only.
8. Получить настоящий ответ и проверить, что текст появляется до завершения turn.
9. Проверить объяснение с «Привет», диагностический cwd и неизменность SHA-256 всех файлов.
10. Закрыть View, дождаться завершения собственного процесса, удалить только тестовый проект и закрыть тестовую EDT.

Это тест в полном EDT, но файл открывается стандартным Eclipse Text Editor в обычном файловом проекте. Он не подменяет ручную проверку специфического BSL-редактора и настоящей конфигурации EDT.

До интеграции также выполнен реальный протокольный probe: handshake, auth, модель, thread, turn, **11 delta**, неизменный BSL-файл и выход процесса с кодом 0.

## Ручная проверка в настоящем проекте EDT

Автор уже подтвердил работу панели и контекста версии 0.1 в EDT 2026.1.3: закрепление справа, Send, проект `Конфигурация1`, модуль `/Конфигурация1/src/CommonModules/ОбщийМодуль/Module.bsl` и выделение `Сообщить("Привет");`.

Для приёмки версии 0.2:

1. Закрыть старую development EDT и выполнить `scripts/start-dev-edt.ps1`.
2. Открыть или импортировать тестовый проект EDT.
3. Открыть Codex: **Window → Show View → Other… → Codex → Codex**, закрепить справа.
4. Дождаться «Codex: подключён — только чтение». Проверить версию и модель в диагностике.
5. В BSL-редакторе выделить короткий фрагмент и отправить **«Что делает выделенный код?»**.
6. Проверить постепенное появление объяснения, блокировку Send на время ответа и его восстановление.
7. Проверить физический каталог проекта в диагностике и отсутствие изменений исходных файлов.
8. Переключиться на модуль другого проекта и повторить: cwd должен измениться.
9. Закрыть панель и открыть снова; подключение должно восстановиться без оставленного прежнего app-server.

При отсутствии входа выполните штатный `codex login` и нажмите **Переподключить**. При отсутствии executable используйте параметр `-CodexExecutable`; см. [build.md](build.md). Stack trace находится в Eclipse Error Log; пользователю показывается короткое сообщение.

## Исправления, найденные проверками

- ID JSON-RPC теперь нормализуются с учётом типа: числовые ID Gson после разбора не теряют соответствие запросу.
- Тестовый сервер получает целый Gson bundle в classpath.
- Тестовый bundle активируется при запуске проверки через extension point EDT.
- Очередь операций завершает ожидающие future при закрытии панели.
- Таймер SWT-теста отменяется до уничтожения виджетов.
- Закрытие заблокированного STDIN выполняется отдельно от ограниченного ожидания процесса.

## Ограничения и диагностика

Ошибок компиляции, тестов и p2 verification в успешных проверках нет.

В журнале EDT встречаются сообщения существующих подсистем: отсутствующий `wmic` в Windows 11, дублирующееся расширение ServersView и отсутствующий working-set filter Resource Navigator. У Codex наблюдались предупреждения о неподдерживаемом PowerShell shell snapshot, единичной неудаче предварительного сетевого соединения и отправке уведомления уже закрывающемуся клиенту. Реальный ответ при этом получен. Эти сообщения не скрываются из локальных журналов.

Tycho предупреждает о пропущенных p2-зависимостях при создании consumer POM. OSGi classpath и runtime разрешены успешно.

Установка ZIP в основную пользовательскую EDT через GUI не выполнялась: её среда не изменяется автоматически. PDE Debug, EDT 2026.2/Java 25, другие ОС, Compare Editor и редакторы без публичного адаптера ITextEditor отдельно не проверены.

Запись, Apply / Reject, diff, approvals UI, выбор модели, кнопка отмены и сохранённая история пока отсутствуют. Совместимость с другой версией Codex требует повторного исследования schema и тестов.
